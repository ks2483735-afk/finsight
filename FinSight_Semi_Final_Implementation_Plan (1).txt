FINSIGHT — SEMI-FINAL IMPLEMENTATION PLAN
===========================================

Open-source • Local-first • BYOK • Finance Research Terminal

1. CORE PHILOSOPHY
------------------
- Free to use and open source.
- Local-first: run on the user's own computer without requiring a FinSight-owned server.
- Bring Your Own Keys (BYOK): users provide their own API keys.
- Provider-independent: AI, market-data, news, and macro providers use adapters.
- Finance-focused AI research terminal.
- Support US and Indian markets initially.
- Provide useful zero-key functionality where public/no-key sources are legally and technically suitable.
- Cloud deployment and cloud synchronization are optional.

2. OVERALL ARCHITECTURE
-----------------------
FinSight
  -> Web Client
  -> FinSight API / AI Orchestrator
      -> AI Router
      -> Data Router
      -> News Router
  -> Provider Adapters
      -> AI providers
      -> Market-data providers
      -> News providers
      -> Public/RSS/filing sources
  -> Normalized data
  -> Dashboard / Research / Alerts

4A. FRONTEND DESIGN SYSTEM — NON-NEGOTIABLE
-------------------------------------------
Frontend design is a first-class implementation requirement, not a final polishing step.

Overall aesthetic:
- Dark, premium, minimal financial-terminal aesthetic.
- Design principles inspired by modern products such as Claude, Vercel, Linear, and professional trading terminals.
- Do not directly copy another product's UI.
- Target: professional financial terminal + modern AI product.
- Avoid excessive neon/cyberpunk styling, random gradients, or decorative effects.

Core visual system:
- Dark background
- Clean panels
- Subtle borders
- Strong typography hierarchy
- Dense but readable financial information
- One controlled accent color
- Clear positive/negative/neutral financial states

Suggested base tokens:
- Background: #0A0A0A
- Secondary background: #111111
- Cards: #151515
- Borders: #242424
- Primary text: #F5F5F5
- Secondary text: #A1A1AA
- Muted text: #71717A
- Positive: green
- Negative: red
- Neutral: gray
- Accent: one controlled project accent

MAIN LAYOUT:
- Persistent left sidebar on desktop.
- Top header with FinSight branding, global search, settings, and user/local-state controls.
- Main workspace with consistent page margins and spacing.
- Sidebar supports expanded and collapsed modes.
- Active navigation item must be visually obvious.
- Responsive behavior for desktop, laptop, tablet, and mobile.

MAIN NAVIGATION:

COMPONENT SYSTEM:
Create reusable components before building many feature pages:
- Button
- Input

Rule:
- Feature pages must reuse the shared component system.
- Do not let every AI-generated page invent its own buttons, cards, spacing, colors, typography, or navigation.

TYPOGRAPHY:
- Establish a global type scale.
- Use clear hierarchy between page titles, section headings, metrics, labels, body text, and metadata.
- Financial numbers should be highly legible.
- Avoid excessive font sizes or decorative typography.

SPACING:
- Define consistent spacing tokens.
- Use a shared grid and container system.
- Avoid arbitrary per-page margins and padding.

CHARTS:
- Charts should be clean, readable, and consistent.
- Use the same chart controls and visual conventions throughout the application.
- Do not overload charts with unnecessary effects.

ANIMATION RULES:
DO:
- Subtle hover transitions.
- Smooth page transitions where useful.
- Chart loading/transition effects.
- Skeleton loading.
- Dropdown/modal transitions.
- Sidebar transitions.
- Subtle button feedback.

DO NOT:
- Excessive glow effects.
- Huge animations.
- Animated gradients everywhere.
- Bouncing cards.
- Particle effects unless there is a specific functional reason.
- Excessive spinners.
- Animations that interfere with financial data readability or performance.

RESPONSIVE DESIGN:
- Desktop is the primary target.
- Laptop layouts must remain comfortable.
- Tablet layouts should adapt navigation and grids.
- Mobile layouts must remain usable rather than simply shrinking the desktop interface.
- Tables and charts need deliberate mobile behavior.

UI STATES:
Every major component/page should account for:
- Loading
- Loaded
- Empty
- Error
- No API key configured
- Provider unavailable
- Partial data
- Stale/cached data

DESIGN IMPLEMENTATION ORDER:
1. Define design tokens.
2. Build global layout.
3. Build sidebar and header.
4. Build global search.
5. Build shared component library.
6. Build dashboard shell.
7. Build research UI.
8. Build company/stock UI.
9. Build news UI.
10. Build screener, portfolio, watchlist, and remaining pages.
11. Verify responsive behavior.
12. Polish only after functionality remains stable.

UI CHANGE VERIFICATION PROTOCOL:
This is mandatory for AI coding tools such as Freebuff Cloud.

Whenever a UI change is requested:
1. Identify the exact files/components responsible.
2. Make the requested UI changes.
3. Run/build the application.
4. Open/inspect the resulting page.
5. Verify that the requested visual changes actually appear.
6. Check that existing functionality was not broken.
7. Only then mark the UI task complete.

Avoid vague UI prompts such as:
"Improve the UI."

Prefer precise instructions such as:
"Replace the dashboard header with the FinSight dark-terminal header. Use the existing design tokens. Set the search bar to 48px height, place market metrics below it, remove gradient card backgrounds, use subtle 1px borders, and make the active sidebar state use the FinSight accent color. Verify the changes on /dashboard."

FRONTEND QUALITY GATE:
A feature is not considered complete merely because its backend works.

Before marking a feature complete:
- The intended visual hierarchy exists.
- The feature uses shared FinSight components.
- Loading/empty/error states exist.
- Responsive behavior is checked.
- Typography and spacing follow the design system.
- The requested UI changes are visibly verified.

4. AI SYSTEM
------------
Use an AI Router rather than hard-coding one model provider.

Initial provider adapters:
- Gemini
- AIMLAPI
- BazaarLink
- Other OpenAI-compatible providers where appropriate

Capabilities:
- Provider/model selection
- Optional fallback providers
- Evidence-grounded research
- Structured AI outputs
- Source-aware answers

The AI should analyze retrieved evidence rather than relying only on model memory.

5. API KEY MANAGER
------------------
Settings should allow users to configure:
- AI providers
- Market-data providers
- News providers
- Macro providers

Each provider should have:
- API key field
- Connection test
- Status
- Enabled/disabled state
- Optional model selection

Security:
- Never commit real API keys to GitHub.
- Use local environment variables/local secret storage.
- Include only placeholders in .env.example.
- Do not expose server-side credentials to browser code.

6. MARKET-DATA ABSTRACTION
--------------------------
The UI should call FinSight's normalized API instead of directly calling individual providers.

Example:
UI
 -> /api/stock/AAPL
 -> Market Data Service
 -> Provider Adapter
 -> Alpha Vantage / Yahoo / another provider

Example normalized object:

{
  symbol,
  price,
  currency,
  change,
  changePercent,
  timestamp,
  source
}

This allows providers to be replaced without rebuilding the UI.

22. CACHING
----------
Suggested cache strategy:

Price data
 -> short cache

News
 -> medium cache

Fundamentals
 -> long cache

Historical financials/filings
 -> very long cache where appropriate

Caching reduces API usage and helps users stay within free provider quotas.

23. PROVIDER FALLBACK
---------------------
Example:

Request stock price
 -> Preferred configured provider
 -> Fallback configured provider
 -> Public/no-key source
 -> Cached result
 -> Clear unavailable-data message

Only use providers whose terms permit the intended use.

24. ZERO-KEY MODE
-----------------
A fresh installation should remain useful without API keys wherever legally and technically possible.

Adding provider keys progressively unlocks:
- Additional data
- Additional AI models
- Higher quotas
- Additional provider-specific features

31. KEY ARCHITECTURAL DECISION
------------------------------
Appwrite should NOT be mandatory for v1.

Build the first version as:
Next.js + SQLite + local provider adapters + BYOK.

Appwrite can later become an optional cloud-sync/auth layer.

This keeps FinSight usable with only a laptop and Wi-Fi.

33. IMPLEMENTATION RULE
-----------------------
Do NOT build the entire project as one giant code dump.

Implement and test one layer at a time:

1. Frontend design system + application foundation
2. Provider architecture
3. Market data
4. AI research
5. News
6. Financial intelligence
7. Portfolio/watchlists/alerts
8. Documentation and open-source release

The frontend is not a final polishing phase. The design system and reusable UI components must be established at the beginning and reused throughout development.

The goal is a maintainable project that can evolve rather than a giant untested prototype.
